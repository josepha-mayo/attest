# Project working rules

- This is an unfinished Ring hackathon prototype, not an attendance-verification or EVV-compliant product.
- Keep Attest private until the owner authorizes publication after another data/security review. Runtime SQLite files were removed from published main history; never reintroduce them or push the old history.
- Never commit runtime data, media, private keys, access tokens, authorization codes, or personal account data. Use explicit staging paths and inspect the staged file list. - Preserve the user's local runtime data. Do not reset demo databases or keys without specific approval.
- A runtime has one writer: `instance.acquire_instance_lock(data_dir)` holds `attest.lock` for the process lifetime (non-blocking; contention fails loudly naming the pid). `serve`, `demo`, and every mutating CLI command (`rotate-key`, `revoke-key`, `coverage`, `digest`, `export`, `anchor`, `checkpoint`, `verify-live --sign`, `verify --attest`, `diff --attest`, `attack-demo`, `tamper-demo`, `retention --apply TOKEN`, `journal --baseline`, `deliveries --requeue`, `monitor --journal`) take it; read-only commands (`status`, `journal`, `explain`, `verify`/`diff` without `--attest`, `triage`, `deliveries`, `doctor`, `issuer`, `prove`, `consistency`, `monitor` without `--journal`, `split-demo` — scratch-space only, `judge` — prints only, retention preview) never do; `seed`, `replay`, `stamp`, unsigned `verify-live`, and `monitor --witness` are client-side or write only user-named files — they never open the store and need no lock — `_cli_engine` deliberately does NOT lock (explain uses it), so add the acquire at the mutating call site.
- Keep observations, scheduled expectations, worker self-reports, model output, and human conclusions separate. Observed intervals are not time worked; missing events are not proof of absence. A signature authenticates record integrity under a trusted key, not physical truth.
- Worker-wide check-in tokens are legacy data only. Authentication uses visit-scoped, hashed, expiring grants — single-use for check-in/review writes, multi-use-until-expiry for family view+statement links (`POST /api/visits/{id}/family-link/revoke` journal-deletes the grant; household statements are capped at 10 per visit so a link holder can't fill the shared review chain). Private routes require ATTEST_ADMIN_TOKEN; CLI access logging is disabled to avoid leaking URL tokens.
- Webhook HMAC has no shipped default: `ring_webhook_key=None` fails intake closed (503 at the route, rejected in the inbox worker). `attest demo` mints a per-run key; `attest replay` exits unless ATTEST_RING_WEBHOOK_KEY matches the target server's. Intake also enforces a signed-body freshness window (`webhook_max_age_s`, default 3600): `meta.time` is HMAC-covered, so verbatim replays beyond the window are 401'd even when the dedupe tombstone is gone. Server boot persists the intake posture (`settings.webhook_intake`: armed/polling/max_age_s) so `attest status` and `/integrity` report the *deployment's* webhook truth, not the CLI process env; `/integrity.json` exposes the same self-audit machine-readable. Media is verified against its signed sha256 at serve time — tampered bytes return 410. Media writes publish atomically (temp file + `os.replace`) so a crash can't leave partial bytes that serve-time digest checks would read as tamper; the media root chmods 0700 and files 0600 on POSIX. A reused delivery id with a different body *or signature* is 409 — HMAC is deterministic over identical bytes, so a differing signature is always anomalous; a future-dated `occurred_at` reschedules the delivery at its admissibility instant instead of burning retry budget. Retention never purges `seen_requests` tombstones by default (`retention_seen_days=0`); an explicit positive value opts in. `verify_journal` reports `unpinned_entries` (tail past the newest receipt-pinned head) and counts `untracked_rows` against health — `untracked` names the divergent `table:id` pairs (bounded at 50) so forensics never guesses. Row writes are self-transactional: `_put`/`put_receipt`/`put_review` join an enclosing `@atomic` txn or open their own, so a bare caller (e.g. the poller) can never leave a journaled row pair half-committed. The unauthenticated POST surfaces are rate-limited per client IP by the outermost middleware (`rate_limit_webhook_per_min` default 300, `rate_limit_grant_per_min` default 30; 0 disables): webhook floods get 429 JSON, grant floods get a styled 429 — the bucket is in-process per worker, so a multi-worker deploy still needs a shared limiter upstream.
- One ingestion source is bound per site. Cross-source deduplication is not implemented; switching requires explicit reconciliation. `POST /api/sites/{id}/disconnect` revokes a site's Ring source: it tombstones the binding (kept as historical fact), signs a `source_disconnected` receipt naming what was unbound, stops ingestion and Event History polling, and is one-way — reconnecting is a new site. Deliveries arriving after disconnect are still inbox-acknowledged but never bind. Late events must not silently mutate signed records — the late-event test is bound by the ACTIVE visit's watermark first (a newer `no_observation` row sorts newest but must not divert an event the open visit still owns), and an event landing inside a lapsed window flags that record `contradicted_no_observation` — the signed receipt stands; the working row admits the pipeline saw activity there. `sweep`/`check_in` reject naive or future caller-supplied timestamps — a deployment never signs records over unelapsed time. Coverage `events` counts post-dedupe `new_events` (the anchored history window re-returns prior events every poll; rows predating the field mark the count a declared lower bound via `events_lower_bound`), and `blind_spot_seconds` publishes the unwatched remainder so `fraction ≈ 1` never reads as full coverage. Period digests count the half-open `[start, end)` — a boundary arrival belongs to the next digest. Every read feeding a signed payload passes `limit=None` — a listing cap must never truncate a signed claim. Export builders refuse `include_media=False` without `redact_media`, self-check that the manifest's signed `visit_id`/`receipt_id`/`reviews` labels match the bundles they name, snapshot `receipts()` once, and derive countersign from the shipped bundle — and every export path re-verifies the built bytes under the live lineage before shipping (CLI verify-before-write, HTTP verify-before-serve). Single-visit packs also carry a signed `export_pin.json` (record_type `export_pin`) binding the review chain's completeness — count + tip hash — plus the bundle's signed media digest set; it exists because review entries are not log leaves, so a trimmed chain verified as a valid prefix before the pin named its length. And since a checkpoint's `proofs` map is unsigned, pack exports sign `pack_members` into the checkpoint payload itself — every member the pack declares must be present or every verifier fails closed (a stripped `export_pin.json`/`verifier_manifest.json`/member file can no longer hide behind a deleted proof). A standalone checkpoint doc (CLI `_verify_log_doc`, the browser's lone-document path) carries the same field but does not presence-probe it — there is no pack to test against.
- Successful local emulator tests are not successful official Playground integration tests. Live Playground verification (2026-09-15, expanded 2026-09-30 via a signed `verify-live` sweep) covered users/me, devices, device status, Event History, and media download via a regional `*.phoenix.devices.amazon.dev` redirect — the target is region-specific (eu-south-2 observed), so the client matches on the suffix. Still unverified: webhook delivery (Playground can't reach localhost), contact-sensor ingestion, and real ding/motion events (Playground only surfaces on_demand). `ava.v1:read`-scoped tokens get 403 on app-integrations and 422 on subscriptions; WHEP returns 500 (no hardware can stream on the account) — report these as honest FAILs, never as unverified code. Live AWS inference: all Bedrock calls now authenticate and reach the service but every model/region returns ThrottlingException — the account's on-demand inference quota is effectively zero; a Service Quotas increase request is the only fix (days). The deterministic fallback is verified end-to-end against real AWS failure modes (expired creds → LoginRefreshRequired; quota → ModelThrottledException/ThrottlingException), which is the designed behavior.
- Use PowerShell syntax on this Windows workspace. Do not use bash heredocs.

Windows requires tzdata for zoneinfo. aws-login credentials require botocore[crt]. Availability of an inference profile does not imply model access or quota. `ATTEST_KMS_KEY_ID` envelope-encrypts the signing key under a KMS data key (AES-256-GCM; stored as `attest-ed25519.key.kms.json`); unwrap requires a live Decrypt with the matching encryption context — verified end-to-end against a real CMK. `attest anchor --publish s3://bucket/key` uploads the signed anchor to S3 with the file sha256 + payload hash in object metadata — verified live against a versioned, public-access-blocked bucket. A configured KMS path that can't reach KMS fails loudly rather than downgrading to a plaintext key. `ATTEST_KEY_CUSTODY=dpapi` wraps the PEM under the Windows DPAPI user master key instead (`attest-ed25519.key.dpapi`, bound to user + machine) — verified by a real CryptProtectData round-trip in tests on Windows, skipped elsewhere; requesting it off-Windows or combining it with KMS fails loudly. `rotate-key` persists the successor under whichever posture is configured. `extras/lambda/verify_lambda.py` is deployed in us-east-1 as `attest-verify-pack` (python3.13, no public URL — authenticated invoke only) and verified live 2026-09-18: a clean signed case pack returns `ok:true` and a tampered bundle returns `ok:false` with "payload hash mismatch" — the function runs the pinned verifier copies, never the pack's embedded script.

Fresh published source checkouts pass 795 of 797 collected Attest tests (2 platform-gated skips) and all 93 companion tests in an isolated Windows Python 3.14 environment. CI runs Windows/Linux and Python 3.11/3.14 without live service credentials. Its companion revision and action versions are pinned; update the companion pin only with matching integration verification. The tracked-runtime-file guard is a publication safety control, not a comprehensive secret scanner.

## Known follow-up work

Deployment authentication, live AWS inference, webhook delivery verification, customer validation, product feedback, and the submission video remain unfinished. Failed deliveries can be returned to pending via `POST /api/webhook-queue/requeue` or `attest deliveries --requeue`; `attest deliveries` inspects the inbox. Worker/countersign state is derived from the signed review chain (`countersign_status`) and never signed into payloads. Every poll writes a `poll_observations` row; receipts carry `history_poll_coverage` attesting how much of the window was watched (silence ≠ absence). Poll rows are retention-purgeable — the signed claim outlives the raw log. Ring lifecycle webhooks (`device_offline`/`device_online`/`device_added`/`device_removed`/`subscription_*` device-scoped; `app_integration_*` account-scoped, fanned out per bound site) journal as `coverage_events` — evidence of *why* observation stopped or resumed, never visit cues. `coverage_report(..., site_id=...)` folds them into `interruptions` and marks poll gaps overlapping a same-device or account-scoped interruption `explained` — a recorded cause, still never proof of absence. Raw `coverage_events` rows are retention-purgeable like poll rows; the signed coverage payloads copy the relevant entries in. Post-disconnect lifecycle deliveries are acknowledged but never journaled. `POST /api/sites/{id}/liveview` brokers a WHEP session through the Ring client (unknown/disconnected sites and malformed SDP offers are rejected before the upstream call — the engine validates the `v=` offer itself so pre-request refusals journal nothing, while a reached-but-protocol-violating Ring response journals a `failed` row like any upstream error) and journals a `liveview_sessions` row (site, device, opened/closed, state, failure); `POST /api/sites/{site_id}/liveview/{session_id}/close` re-journals the row on close. A session proves a stream was established at a time — never that anyone watched, what it showed, or who was present. Live frames never enter visit evidence. Sessions overlapping a coverage window are copied into the signed coverage payload (device-matched like interruptions); raw rows purge under `retention_liveview_days`. Record timeline strips (`timeline.py`, `_timeline.html`, and the pack browser's `timelineSVG`) draw a closed session as a teal band over the coverage line and a still-open session as a tick — the same signed payload feeds every surface. `timeline_strip`/`day_strips` take `tz` (the deployment display timezone — ticks and the aria-label must agree with every other local-time rendering on the page) and `tr` (the i18n `tl_*` string table — SVG titles, kind labels, and the screen-reader prose localize with `?lang=`); `day_strips` returns `{"strips", "hidden_days"}` so days beyond the 10-day cap are reported, never silently dropped. `GET /visits/{id}/pack.zip` exports a dispute pack: bundle + media + a stdlib-only verifier (`disputepack._VERIFIER` mirrors ledger canonicalization — keep them in sync) + `verify.html` + `index.html`, dependency-free browser verifier and record browser (Ed25519 via WebCrypto with the pure-BigInt verifier as authoritative fallback (strictness gates shared in JS; _engWc/_engJs name the engine on the verdict) + WebCrypto/JS SHA-256 — keep `verifyjs.py` in sync with ledger canonicalization too; its JS canonicalizer copies non-string literals verbatim so float spellings like `34.0` survive, but re-serializes strings via JSON.stringify so `\uXXXX` escapes and raw UTF-8 canonicalize identically (matching Python's ensure_ascii=False)). The embedded `check_bundle`/`checkBundle` mirror `reviews.verify_bundle` at full strictness (entry id/visit_id, revision==sequence==position, prev_hash, record_type, original_receipt anchor exactly `{id,hash}`) — keep all three in parity. The same-bytes-same-verdict contract is enforced at the model layer, not per-surface: `Receipt.sequence` and `ReviewEntry.revision` are strict JSON integers (`"5"`, `true`, and `5.5` are malformed everywhere — only an integral `5.0` equals 5), `Receipt.prev_hash` is required-nullable (absent ≠ explicit `null`), `issued_at` parses through the shared ASCII `ISO_INSTANT_RE` grammar on every surface (no `Date.parse`, no Unicode digits, naive ≠ aware), and the browser verifier compares integers through each literal's verbatim spelling (`BigInt`) so sequences past 2⁵³ can't alias — when any of these rules move, mirror them into the embedded `_py_model_int`/`_iso_instant`/`_py_eq` helpers AND `verifyjs.py`'s `_pyModelInt`/`_pyInstant`/`_pyEqN`, regenerate `docs/verify.html` + the sample pack, and re-run the `test_parity_r*.py` oracles. Signature verification itself is canonicality-gated before OpenSSL on every Python path (`ledger._canonical_point` mirrors the browser `decodePoint`: `y < p`, `x = 0 ⟹ sign = 0`, `S < L` — OpenSSL's ref10 family otherwise accepts the `S = 0, R =` identity forgery under small-order encodings) and `Receipt.id` is required (never default-minted — a missing `id` is malformed everywhere, not silently generated). `GET /sites/{id}/pack.zip` exports a case pack — every signed visit for the site plus a manifest of receipt hashes and worker stances, verified offline by `verify_case.py` or `/verify`. Two distinct files share the name `verify.html`: `templates/verify.html` is the server's upload form at `/verify`; the pack's embedded `verify.html` (generated by `verifyjs.py`, also served standalone at `/verify-pack`) is the dependency-free verifier — they do different things and are not interchangeable. When a signer is available, the manifest itself is signed as a `case_export` receipt (idempotent via an `export:{site}:{manifest_sha256[:16]}` pseudo-visit): the receipt names the exact `visit_id → payload_hash` map and the canonical `manifest_sha256` (hashed without `signature_receipt`), so a dropped or swapped record fails closed; pre-signature packs report "unsigned manifest" rather than failing. Site-level chain events — `source:{site}` disconnects, `coverage:{site}:…`, `digest:{site}:…`, `verify:{digest}` verification reports, `key:*` rotation/adoption receipts, `monitor:*` observation receipts, `pack-verify:*`/`pack-diff:*` verdict-and-comparison attestations, and prior `export:{site}:…` receipts — are collected before the manifest is signed and travel as `attestations/{receipt_id}.json`, listed in the manifest's `attestations` array (receipt_id + visit_id + payload_hash + record_type); every verifier (embedded `verify_case.py`, `verify.html`, `index.html`, `_verify_pack`) checks each against the issuer key and the manifest entry, and an attestation file the manifest does not list fails closed — the export's own manifest receipt is the one attestation a pack cannot carry, since it cannot reference its own hash. `verifier_manifest.json` is the other signed member: a `verifier_manifest` receipt (idempotent via an `export-tools:{sha256[:16]}` pseudo-visit — deliberately not `export:{site.id}:` so a site named `tools` can't absorb them as attestations) whose payload pins the sha256 of every verifier tool the pack ships — `verify_case.py`/`verify_bundle.py`, `verify.html`, `index.html`, `README.txt` — with a `scope` bound to the pack (`visit:{id}`/`site:{id}`). Member whitelists check names; only the pin binds bytes, so a forged always-green verifier riding a genuine pack fails closed, as do a scope graft, a foreign signer, a pinned member absent, or a tool present but unpinned. Legacy packs without the member pass with no pin note — optional when absent, mandatory when present. `verify --attest pack.zip` signs the verdict itself into the deployment's journal — a `pack_verification` receipt (idempotent via a `pack-verify:{sha256(every asserted claim + trust context)[:16]}` pseudo-visit — a re-run reaching a different verdict never reuses it) binding sha256(pack bytes), the ok/fail verdict, the detail string, the trust context it ran under (issuer pin, lifecycle-pool fingerprint, witness policy, live-log result), and the verifier's content identity (name/version/checker + module-source hash) — a mediator's audit becomes auditable, and FAIL verdicts sign too: a forged pack attested as forged is evidence. The receipt never claims the verdict is right — anyone can re-run the pinned verifier on the named bytes — `diff --attest old.zip new.zip` signs the comparison the same way — a `pack_comparison` receipt (idempotent via `pack-diff:{sha256(every asserted claim + trust context)[:16]}` — the digests are bound from the verified load, not a path re-read) binding both pack digests, the machine verdict (`log_heads` kind + anomaly count), and an events-stream hash — the mediator's "the log provably grew / these fields moved" is evidence too.
