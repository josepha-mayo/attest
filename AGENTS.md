# Project working rules

- This is an unfinished Ring hackathon prototype, not an attendance-verification or EVV-compliant product.
- Keep Attest private until the owner authorizes publication after another data/security review. Runtime SQLite files were removed from published main history; never reintroduce them or push the old history.
- Never commit runtime data, media, private keys, access tokens, authorization codes, or personal account data. Use explicit staging paths and inspect the staged file list. Runtime folders must be ignored even when their names differ from `data/`. One deliberate exception: `docs/sample-pack.zip` is a small redacted pack of simulated data shipped so the hosted verifier's landing page can offer a zero-install try — regenerate it via `attest demo` + `attest export --redact-media` when the pack format changes. `docs/live-sweep-receipt.json` is likewise a deliberate artifact: the signed `verify-live --sign` report from the real `api.amazonvision.com` run on 2026-09-30 (no tokens, masked device id, media digest only) — it exists so judges can verify the real-API claim offline; never regenerate it from emulator output.
- Preserve the user's local runtime data. Do not reset demo databases or keys without specific approval.
- A runtime has one writer: `instance.acquire_instance_lock(data_dir)` holds `attest.lock` for the process lifetime (non-blocking; contention fails loudly naming the pid). `serve`, `demo`, and every mutating CLI command (`rotate-key`, `revoke-key`, `coverage`, `digest`, `export`, `anchor`, `verify-live --sign`, `attack-demo`, `tamper-demo`, `retention --apply`, `journal --baseline`, `deliveries --requeue`) take it; read-only commands (`status`, `journal`, `explain`, `verify`, `diff`, `triage`, `deliveries`, `doctor`, `issuer`, retention preview) never do — `_cli_engine` deliberately does NOT lock (explain uses it), so add the acquire at the mutating call site.
- Keep observations, scheduled expectations, worker self-reports, model output, and human conclusions separate. Observed intervals are not time worked; missing events are not proof of absence. A signature authenticates record integrity under a trusted key, not physical truth.
- Worker-wide check-in tokens are legacy data only. Authentication uses visit-scoped, hashed, expiring grants — single-use for check-in/review writes, multi-use-until-expiry for family view+statement links (`POST /api/visits/{id}/family-link/revoke` journal-deletes the grant; household statements are capped at 10 per visit so a link holder can't fill the shared review chain). Private routes require ATTEST_ADMIN_TOKEN; CLI access logging is disabled to avoid leaking URL tokens.
- Webhook HMAC has no shipped default: `ring_webhook_key=None` fails intake closed (503 at the route, rejected in the inbox worker). `attest demo` mints a per-run key; `attest replay` exits unless ATTEST_RING_WEBHOOK_KEY matches the target server's. Intake also enforces a signed-body freshness window (`webhook_max_age_s`, default 3600): `meta.time` is HMAC-covered, so verbatim replays beyond the window are 401'd even when the dedupe tombstone is gone. Server boot persists the intake posture (`settings.webhook_intake`: armed/polling/max_age_s) so `attest status` and `/integrity` report the *deployment's* webhook truth, not the CLI process env; `/integrity.json` exposes the same self-audit machine-readable. Media is verified against its signed sha256 at serve time — tampered bytes return 410. Media writes publish atomically (temp file + `os.replace`) so a crash can't leave partial bytes that serve-time digest checks would read as tamper; the media root chmods 0700 and files 0600 on POSIX. A reused delivery id with a different body *or signature* is 409 — HMAC is deterministic over identical bytes, so a differing signature is always anomalous; a future-dated `occurred_at` reschedules the delivery at its admissibility instant instead of burning retry budget. Retention never purges `seen_requests` tombstones by default (`retention_seen_days=0`); an explicit positive value opts in. `verify_journal` reports `unpinned_entries` (tail past the newest receipt-pinned head) and counts `untracked_rows` against health. The unauthenticated POST surfaces are rate-limited per client IP by the outermost middleware (`rate_limit_webhook_per_min` default 300, `rate_limit_grant_per_min` default 30; 0 disables): webhook floods get 429 JSON, grant floods get a styled 429 — the bucket is in-process per worker, so a multi-worker deploy still needs a shared limiter upstream.
- One ingestion source is bound per site. Cross-source deduplication is not implemented; switching requires explicit reconciliation. `POST /api/sites/{id}/disconnect` revokes a site's Ring source: it tombstones the binding (kept as historical fact), signs a `source_disconnected` receipt naming what was unbound, stops ingestion and Event History polling, and is one-way — reconnecting is a new site. Deliveries arriving after disconnect are still inbox-acknowledged but never bind. Late events must not silently mutate signed records.
- Successful local emulator tests are not successful official Playground integration tests. Live Playground verification (2026-09-15, expanded 2026-09-30 via a signed `verify-live` sweep) covered users/me, devices, device status, Event History, and media download via a regional `*.phoenix.devices.amazon.dev` redirect — the target is region-specific (eu-south-2 observed), so the client matches on the suffix. Still unverified: webhook delivery (Playground can't reach localhost), contact-sensor ingestion, and real ding/motion events (Playground only surfaces on_demand). `ava.v1:read`-scoped tokens get 403 on app-integrations and 422 on subscriptions; WHEP returns 500 (no hardware can stream on the account) — report these as honest FAILs, never as unverified code. Live AWS inference: all Bedrock calls now authenticate and reach the service but every model/region returns ThrottlingException — the account's on-demand inference quota is effectively zero; a Service Quotas increase request is the only fix (days). The deterministic fallback is verified end-to-end against real AWS failure modes (expired creds → LoginRefreshRequired; quota → ModelThrottledException/ThrottlingException), which is the designed behavior.
- Use PowerShell syntax on this Windows workspace. Do not use bash heredocs.

## Verification

Run from this repository:

- `.\.venv\Scripts\python -m pytest -q`
- `.\.venv\Scripts\ruff check src tests`
- `.\.venv\Scripts\ruff format --check src tests`
- `git diff --check`

The sibling ring-sandbox project has the same commands in its own environment. Its pytest fixtures auto-load through a pytest11 entry point; do not also register that plugin in conftest.py.

Install with the pinned tested set: `.\.venv\Scripts\python -m pip install -r requirements-dev.txt -e ".[dev]"` — the lock pins `ring-sandbox==0.5.0` from PyPI, so a standalone clone works without the sibling repo; add `-e "../ring-sandbox[server]"` only when developing the emulator alongside (its version must still satisfy the pin). `requirements-dev.txt` is the reproducibility lock; regenerate it after deliberate dependency upgrades. The client's `send(stream=True)` and manual redirect handling require httpx>=0.28.

Windows requires tzdata for zoneinfo. aws-login credentials require botocore[crt]. Availability of an inference profile does not imply model access or quota. `ATTEST_KMS_KEY_ID` envelope-encrypts the signing key under a KMS data key (AES-256-GCM; stored as `attest-ed25519.key.kms.json`); unwrap requires a live Decrypt with the matching encryption context — verified end-to-end against a real CMK. `attest anchor --publish s3://bucket/key` uploads the signed anchor to S3 with the file sha256 + payload hash in object metadata — verified live against a versioned, public-access-blocked bucket. A configured KMS path that can't reach KMS fails loudly rather than downgrading to a plaintext key. `ATTEST_KEY_CUSTODY=dpapi` wraps the PEM under the Windows DPAPI user master key instead (`attest-ed25519.key.dpapi`, bound to user + machine) — verified by a real CryptProtectData round-trip in tests on Windows, skipped elsewhere; requesting it off-Windows or combining it with KMS fails loudly. `rotate-key` persists the successor under whichever posture is configured. `extras/lambda/verify_lambda.py` is deployed in us-east-1 as `attest-verify-pack` (python3.13, no public URL — authenticated invoke only) and verified live 2026-09-18: a clean signed case pack returns `ok:true` and a tampered bundle returns `ok:false` with "payload hash mismatch" — the function runs the pinned verifier copies, never the pack's embedded script.

Fresh published source checkouts pass 465 of 470 collected Attest tests (5 platform-gated skips) and all 93 companion tests in an isolated Windows Python 3.14 environment. CI runs Windows/Linux and Python 3.11/3.14 without live service credentials. Its companion revision and action versions are pinned; update the companion pin only with matching integration verification. The tracked-runtime-file guard is a publication safety control, not a comprehensive secret scanner.

## Known follow-up work

Deployment authentication, live AWS inference, webhook delivery verification, customer validation, product feedback, and the submission video remain unfinished. Failed deliveries can be returned to pending via `POST /api/webhook-queue/requeue` or `attest deliveries --requeue`; `attest deliveries` inspects the inbox. Worker/countersign state is derived from the signed review chain (`countersign_status`) and never signed into payloads. Every poll writes a `poll_observations` row; receipts carry `history_poll_coverage` attesting how much of the window was watched (silence ≠ absence). Poll rows are retention-purgeable — the signed claim outlives the raw log. Ring lifecycle webhooks (`device_offline`/`device_online`/`device_added`/`device_removed`/`subscription_*` device-scoped; `app_integration_*` account-scoped, fanned out per bound site) journal as `coverage_events` — evidence of *why* observation stopped or resumed, never visit cues. `coverage_report(..., site_id=...)` folds them into `interruptions` and marks poll gaps overlapping a same-device or account-scoped interruption `explained` — a recorded cause, still never proof of absence. Raw `coverage_events` rows are retention-purgeable like poll rows; the signed coverage payloads copy the relevant entries in. Post-disconnect lifecycle deliveries are acknowledged but never journaled. `POST /api/sites/{id}/liveview` brokers a WHEP session through the Ring client (unknown/disconnected sites and malformed SDP offers are rejected before the upstream call) and journals a `liveview_sessions` row (site, device, opened/closed, state, failure); `POST /api/sites/{site_id}/liveview/{session_id}/close` re-journals the row on close. A session proves a stream was established at a time — never that anyone watched, what it showed, or who was present. Live frames never enter visit evidence. Sessions overlapping a coverage window are copied into the signed coverage payload (device-matched like interruptions); raw rows purge under `retention_liveview_days`. Record timeline strips (`timeline.py`, `_timeline.html`, and the pack browser's `timelineSVG`) draw a closed session as a teal band over the coverage line and a still-open session as a tick — the same signed payload feeds every surface. `timeline_strip`/`day_strips` take `tz` (the deployment display timezone — ticks and the aria-label must agree with every other local-time rendering on the page) and `tr` (the i18n `tl_*` string table — SVG titles, kind labels, and the screen-reader prose localize with `?lang=`); `day_strips` returns `{"strips", "hidden_days"}` so days beyond the 10-day cap are reported, never silently dropped. `GET /visits/{id}/pack.zip` exports a dispute pack: bundle + media + a stdlib-only verifier (`disputepack._VERIFIER` mirrors ledger canonicalization — keep them in sync) + `verify.html` + `index.html`, dependency-free browser verifier and record browser (pure-BigInt Ed25519 + WebCrypto hashes — keep `verifyjs.py` in sync with ledger canonicalization too; its JS canonicalizer copies non-string literals verbatim so float spellings like `34.0` survive, but re-serializes strings via JSON.stringify so `\uXXXX` escapes and raw UTF-8 canonicalize identically (matching Python's ensure_ascii=False)). The embedded `check_bundle`/`checkBundle` mirror `reviews.verify_bundle` at full strictness (entry id/visit_id, revision==sequence==position, prev_hash, record_type, original_receipt anchor id+hash) — keep all three in parity. `GET /sites/{id}/pack.zip` exports a case pack — every signed visit for the site plus a manifest of receipt hashes and worker stances, verified offline by `verify_case.py` or `/verify`. Two distinct files share the name `verify.html`: `templates/verify.html` is the server's upload form at `/verify`; the pack's embedded `verify.html` (generated by `verifyjs.py`, also served standalone at `/verify-pack`) is the dependency-free verifier — they do different things and are not interchangeable. When a signer is available, the manifest itself is signed as a `case_export` receipt (idempotent via an `export:{site}:{manifest_sha256[:16]}` pseudo-visit): the receipt names the exact `visit_id → payload_hash` map and the canonical `manifest_sha256` (hashed without `signature_receipt`), so a dropped or swapped record fails closed; pre-signature packs report "unsigned manifest" rather than failing. Site-level chain events — `source:{site}` disconnects, `coverage:{site}:…`, `digest:{site}:…`, `verify:{digest}` verification reports, `key:*` rotation/adoption receipts, and prior `export:{site}:…` receipts — are collected before the manifest is signed and travel as `attestations/{receipt_id}.json`, listed in the manifest's `attestations` array (receipt_id + visit_id + payload_hash + record_type); every verifier (embedded `verify_case.py`, `verify.html`, `index.html`, `_verify_pack`) checks each against the issuer key and the manifest entry, and an attestation file the manifest does not list fails closed — the export's own manifest receipt is the one attestation a pack cannot carry, since it cannot reference its own hash. `?redact_media=1` (or `attest export --redact-media`) withholds media bytes: a `redaction.json` marker lists the withheld signed digests, the manifest records `media_redacted`, and verifiers report them withheld rather than missing — a redaction file naming digests absent from the signed evidence fails closed. Every zip-reading verifier first rejects ambiguous member names — duplicates, `..` segments, absolute or drive-qualified paths (`packdiff.check_member_names` is the canonical check; `_verify_pack`/`_verify_case_pack` and the browser verifier's `readZipEntries` enforce the same rule — keep all three in parity). The embedded `verify_bundle.py`/`verify_case.py` sweep extracted pack dirs for files outside the pack format and never die with a traceback — unexpected exceptions exit as `FAIL verifier error: …` so a verifier crash always reads as a failed verification, not a pass. `attest verify bundle.json` runs the same checks offline. `attest explain VISIT_ID` renders one record in human terms — source-by-source corroboration, the signed receipt anchor, the review chain, and the derived stance. `attest diff A B` compares two exports (case packs, dispute packs, or bare bundles): each artifact's signed contents verify first, new visits and appended reviews are normal drift, and a vanished record, altered signed payload, removed review, or manifest/bundle hash disagreement is an anomaly; `--key` pins verification to a trusted issuer instead of the pack's self-declared key. `attest attack-demo` runs a tamper battery inside rolled-back transactions. THREATMODEL.md is the canonical statement of what records prove and the detection path per attack — keep it in sync with verifier semantics. Every issued receipt signs `journal_head` — the hash of the mutation journal's tip at issuance — so `verify_journal` detects tail truncation as well as edits, deletions, and interior gaps; pre-pin receipts simply leave that check uncovered. `verify_journal` also re-derives every denormalized index column (token_hash, visit_id, state, polled_at, …) from the signed body and flags divergence — a direct column UPDATE cannot evade detection; `late_events` binds `site_id` into the journaled row hash itself (pre-binding rows hashed the body alone and are still accepted, with site_id unauthenticated). `attest coverage --site S --from T0 --to T1` signs a coverage attestation for an arbitrary interval (fraction watched, poll/event counts, explicit gaps) via the normal receipt chain — silence is never conflated with absence of watching. `attest anchor --out FILE` writes a standalone signed checkpoint pinning the journal head and receipt-chain head; `attest verify FILE` auto-detects bundles, anchors, and coverage receipts. `attest rotate-key` retires the deployment signing key: the retiring key signs a `key_rotation` receipt endorsing its successor, the successor lands under the same custody posture, then countersigns a `key_adoption` naming the rotation (id + payload hash). `verify_chain` pivots at the rotation; every verifier (server, embedded, JS, packdiff) extends pinned-key trust through `trusted_issuer_keys`/`descendant_issuer_keys` — ancestors require the successor's adoption countersignature (endorsement alone is self-serve; a grafted "predecessor" never enters the set), descendants require the trusted key's own endorsement. Packs carry `key:*` receipts as attestations (case packs) or `key_rotations.json` (dispute packs); `ReviewService.trusted_issuer_keys` derives the live set so post-rotation bundles verify. `POST /api/admin/rotate-key` performs the same ordered pivot on the running deployment (the handler rebinds engine/reviews/app.state signers after custody takes); `attest demo --rotate-day K` exercises that endpoint mid-story, and `docs/sample-pack.zip` is regenerated with a rotation so the shipped pack always demonstrates mixed-key verification. `errors.DomainError` carries a stable `code` — route handlers branch on it for localized/conflict responses; never match on exception message text. `attest anchor --timestamp` / `attest stamp FILE` notarize a file's sha256 on the public OpenTimestamps calendars (writes FILE.ots); `attest stamp --upgrade FILE.ots` refreshes a pending proof — a 404 from the calendar means reachable-but-not-yet-committed, not unreachable. We submit/wrap/upgrade/detect-status only; proof validation belongs to the reference `ots` tool. `attest verify` reports a sibling FILE.ots automatically. `attest status` audits a runtime offline (journal, receipt chain, coverage, inbox) and exits non-zero on failure; `--json` emits the same audit machine-readable, mirroring `/integrity.json`. `attest verify-live [--out FILE]` sweeps the official API with a live token — users/me, app-integration, subscriptions, devices(+capabilities/status), Event History, media download, and a WHEP open+close — printing per-check PASS/FAIL/SKIP with the API's own errors; token_hint is masked and only PASS counts as verified. `--sign` issues the report into the chain as a `verification_report` receipt (idempotent via `verify:{sha16}` pseudo visit_id; `--out` writes the signed receipt). `attest triage` / `POST /api/triage` (dashboard "Run agent brief") writes the week's needs-attention brief: a Strands agent reads the ledger through read-only tools when the `agent` extra + Bedrock credentials are available, else the deterministic brief — the result always labels its source (`strands-agent` + model id, or `deterministic` + fallback reason). The agent never writes records, its system prompt forbids presence/absence claims and declares record content untrusted data (instructions inside statement fields must never be obeyed), and the agentic loop is capped at `limits={"turns": 12}` so a looping model can't burn quota for minutes. `attest digest --from T --to T` / `POST /api/sites/{id}/digest` signs a `period_digest` receipt — counts of records written in the interval by outcome and review stance, plus the exact `summarized_receipts` map; idempotent per site+range via a `digest:` pseudo visit_id, and a statement about the ledger, never physical presence. The sweep loop also self-issues digests on `ATTEST_DIGEST_INTERVAL_S` (default 604800, 0 disables): a new digest continues exactly from the previous window's end; a site with no history seeds the trailing interval. `attest explain <id> --json` emits the same record account machine-readable (sources, anchors, review chain, stance). `attest demo` boots the in-process emulator + server + a `--story` replay behind a ready Basic-auth URL — one command for the full simulated dataset. After the replay it signs a coverage attestation over the story window and a `verification_report` sweep against the emulator (honestly labeled `127.0.0.1`), so packs and the integrity page carry the same provenance shape a real `verify-live --sign` produces. `attest demo --chaos` injects webhook duplication + delivery jitter (seeded, no drops — a lost event would silently rewrite the story); the ledger must still show one evidence row per real event. `attest demo --open` launches the authenticated dashboard in the default browser once live. The companion emulator's `ring-sandbox serve --chaos` injects duplicated/dropped/delayed webhook deliveries and flaky history/media responses; `GET|POST /_sandbox/chaos` inspects and adjusts the fault stream live — used to prove Attest's dedupe and durable inbox under unreliable delivery. The client supports an RFC 6749 refresh grant (`ATTEST_RING_REFRESH_TOKEN`, `ATTEST_RING_CLIENT_ID`, `ATTEST_RING_TOKEN_URL`); on 401 it refreshes once and retries, persisting rotated tokens under the `ring_auth` store setting. Production OAuth endpoints are not yet verified — the refresh path is exercised against the emulator only. Media redirects are manually validated: JSON endpoints never follow redirects, media redirects only reach same-origin or `ring_media_origins` allowlisted HTTPS hosts, never carry credentials, and bodies are byte-capped. Request bodies, verification inputs, and link/ID path parameters are size-bounded. `attest retention` / `GET /api/retention` preview lifecycle candidates; `attest retention --apply TOKEN` / `POST /api/retention/apply` delete only the previewed non-chain set (deliveries, grants, dedupe keys, late events, poll rows, coverage events, live-view sessions, media files) when the confirm token matches — chain-linked visits/receipts are never deleted in place. Webhook intake acknowledges a durable separate inbox before background processing; `test_webhook_intake_meets_ring_deadline` bursts 40 signed deliveries through the real app and asserts every ack lands far under Ring's ~5s deadline; failed-delivery replay tooling beyond `deliveries --requeue` remains pending. All Ring/Bedrock calls run OUTSIDE the write transaction — `ingest`/`sweep`/`close_for_review` prefetch snapshots, history, and summaries against committed reads before the `@atomic` apply, which re-validates a token (last_activity_at, evidence count, receipt absence) and degrades to the same media_unavailable/template-summary/no-history outcomes a failed fetch produces, so a hung upstream can never hold the store lock (`test_ring_calls_never_inside_write_txn`); `close_liveview` splits read → `whep_close` → mark-closed across two short txns, and the dashboard's journal verdict is cached 15s keyed on journal head (`/integrity` and `attest status` always run the full uncached audit). Pack verifiers fail closed on ANY zip member the signed manifest/pack format doesn't name — top-level extras, files inside a listed visit dir, and media members whose bytes don't hash to a signed evidence digest all fail (`test_verify_pack_rejects_smuggled_top_level_and_media`); keep `_verify_case_pack`, `packdiff.load_artifact`, embedded `verify_case.py`, and `verifyjs.py` enumeration in parity. Naive (non-tz-aware) `occurred_at`/`meta.time` is rejected at webhook intake (400) rather than burning inbox retries on a TypeError. Future-dated `occurred_at` (past the 30s skew tolerance) raises `NotYetAdmissible` — the inbox reschedules to the admissibility instant instead of dead-lettering on early arrivals. A row that fails to parse raises `StoreCorrupt` — reads never silently skip tampered bodies: the CLI exits with a single error line (`attest status`, `journal`, `verify`, `coverage`, `digest`, `explain`), the web surfaces render a styled 500 pointing at `/integrity`, and `verify_journal` names the divergent rows. Non-dict `settings` bodies fail the same way. `attest journal`/`tamper-demo`/`export`/`retention` refuse a missing database — SQLite must never mint an empty store and report it intact. Enabling `ATTEST_KMS_KEY_ID` on a deployment that already has a plaintext `attest-ed25519.key` wraps THAT key (same issuer identity; the PEM is removed only after the wrapped record is written) — minting a fresh key would silently rotate the issuer and strand every signed record; unreachable KMS fails before the PEM is touched. `corroboration()` renders a visit whose site row is gone from the receipt's signed `site` block, labeled unavailable. `attest coverage`/`digest` refuse inverted windows (`end <= start`) rather than signing an empty claim, and `coverage_report`'s `no_window` shape carries the same keys as a normal report. Signed coverage/digest payloads read every `coverage_events`/`liveview_sessions` row (`limit=None`) — a silent 500-row cap would over-explain gaps past the cap; UI callers keep explicit bounds. `attest explain <attestation> --json` emits the same machine-readable record as for visits (`spans_visit_window` is computed on parsed datetimes — a caller-controlled `-07:00` offset can't mis-sort against UTC). `.ots` proofs write-then-rename (no truncated proofs on crash) and the sibling-`.ots` check is skipped for URL artifacts — a remote basename must never match an unrelated CWD file. `packdiff.load_artifact` flags a malformed manifest entry or bundle member per-record instead of aborting the whole diff — the rest of the anomalies still report. `attest rotate-key` retires the deployment signing key as a chain event: the retiring key signs a `key_rotation` receipt (`key:{old[:12]}:{new[:12]}` pseudo-visit, idempotent) naming its successor — the ledger's pivot — `persist_signer_key` then atomically writes the successor under the same custody posture (plaintext PEM or KMS wrap; the old key survives until the new one is durable), and the new key signs a `key_adoption` receipt proving its holder consented. `verify_chain` reads the pivot: receipts before it verify under the retiring key, after it under the successor; a pinned `--key` must be the chain root or a signed-rotation ancestor of it. `trusted_issuer_keys`/`descendant_issuer_keys` (and the embedded `trusted_keys`/`descendant_keys`/`trustedKeys`/`descendantKeys` mirrors) walk the signed links only — each hop must verify under the retiring key, so a forged or self-endorsed rotation never lands in the set and a key that merely appears in a pack is never trusted. Case packs carry `key:*` receipts as manifest-listed attestations and `issuer_key` names the CURRENT signer (never a retired key); dispute packs write `key_rotations.json`; every verifier — `_verify_pack`/`_verify_case_pack`, embedded `verify_case.py`/`verify_bundle.py`, and `verifyjs.py` — derives the same trusted set, and `/verify` additionally consults the deployment's own ledger pivots (`known_rotations`) so a pre-rotation pack still verifies under the current key. Keep all of them in parity. `GET /.well-known/attest-issuer.json` is the JWKS analogue: `ledger.issuer_document(...)` serves the current issuer key, every `key:*` lifecycle receipt, and the chain tip — public by design (the material is public verification crypto that rides in every pack anyway); `attest issuer --out` writes the same document for out-of-band exchange, and `attest verify --issuer-url <doc-or-url>` pins verification to it (`_fetch_issuer_doc` takes a URL or a local file; remote loads are HTTPS-only except loopback, and the document's `boundary` field states the TOFU caveat). The fetched `key_receipts` flow in as `known_rotations`, so a pack exported before a rotation verifies against the deployment's CURRENT issuer — the honest remote-pinning path when `--key` fingerprint exchange isn't available. The parity contract is executable: `tests/vectors/` pins fixed real packs plus an `expected.json` oracle each (Wycheproof-style conformance vectors); `tests/test_conformance.py` judges every pack through the server verifier, the embedded stdlib scripts, and the JS lib under node — a disagreement is a verifier bug, never an oracle tweak. `tools/make_vectors.py` regenerates the corpus when the pack format deliberately changes (fixed Ed25519 seeds keep issuer identities stable); never hand-edit the zips, and `.gitattributes` keeps them `-text` so CRLF can't corrupt the bytes.

Coordinated replay is now explicit (`ATTEST_REPLAY_MODE=true`) and only accepts loopback Ring emulators in a fresh runtime; `attest replay` also resets the emulator's world so stale history cannot bind the site to the wrong ingest source. `attest replay home_aide_visit --speed 60 --auto-checkin` seeds a local case and waits for delivery processing before advancing its persisted event clock. Multi-day demos: `--days N` creates one schedule per day (the clock starts N days back — replay time can never exceed wall time), `--no-show-day K` plays no events so the schedule lapses to `no_observation`, `--story p1,p2,...` cycles named day-patterns (`observed`, `late`, `early_out`, `no_show`, `unmatched`, `blackout` — `unmatched` replays events past the window so the visit is unmatched *and* the schedule still lapses; `blackout` drops the camera mid-visit so the departure is unobserved and the signed coverage report carries the device_offline/device_online explanation; `sub_lapse` lapses the Ring plan mid-visit so post-lapse observation steps are dropped (matching real entitlement suppression) and the coverage report carries the subscription_deactivated explanation — a billing fact, not a device fault; `liveview` plays an observed day plus a coordinator live-view session opened mid-window and closed — the journaled session lands in the visit's signed coverage), and `--worker-review confirm|dispute` posts a worker statement on the most recent observed scheduled visit. Custom scenarios: `attest replay path/to/scenario.yml` loads the ring-sandbox YAML DSL; the wheel-shipped examples `late_arrival`, `partial_blackout`, and `visitor_not_worker` resolve by name with no file path. The replay drives `POST /api/poll` between steps so `poll_observations` coverage rows land on the logical timeline. Grant expiry, statement-received time, and signature issuance always use wall time. Do not convert an existing runtime between wall and replay modes.

Worker/coordinator reviews append signed per-visit review chains anchored to the original receipt hash; never rewrite original visits/receipts when correcting an account. Coordinator resolutions (`POST /api/visits/{id}/resolve`, outcomes record_upheld/account_accepted/inconclusive) append the terminal signed conclusion — the worker stance stays in the chain, `countersign_status` derives `resolved` only while the latest resolution post-dates the latest worker statement (a newer statement re-opens), and resolved records leave the attention queue.
